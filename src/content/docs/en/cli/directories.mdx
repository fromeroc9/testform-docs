---
title: "The .testform and ~/.testform.d Directories"
description: "Structure, purpose, and lifecycle of the local .testform working directory and the global ~/.testform.d user configuration."
---

Just as HashiCorp Terraform relies on `.terraform` and `~/.terraform.d`, **Testform** utilizes two dedicated support directories to manage its operational state, local caches, extensions, and user credentials:

1. **`.testform/` (Project Working Directory):** Created in the root of the project workspace where `main.yml` resides. It serves as the local scratch and cache area where Testform stores backend metadata, downloaded modules, ephemeral sandboxes, and discovered extensions.
2. **`~/.testform.d/` (Global User Directory):** Located in the operating system user's home directory. It securely stores authentication credentials and persistent CLI session configurations.

---

## Project Directory Structure (`.testform/`)

```text
my-project/
├── main.yml
├── testform.state
├── .testform.lock.hcl         # Cryptographic provider lockfile (h1: hashes and pinned versions)
└── .testform/
    ├── data.json              # Local mock database for provider: local
    ├── environment            # Name of the currently selected workspace
    ├── cache/                 # Engine auto-generated and disposable cache files
    │   ├── backend.json       # Initialized active backend configuration (testform init)
    │   ├── lock.json          # Provider dependency lock and cryptographic checksums
    │   └── parser-ast.json    # Incremental AST cache for fast .feature parsing
    ├── providers/             # Downloaded and installed provider plugins (testform init)
    │   └── <provider_name>/
    │       ├── index.js / provider.ts
    │       └── package.json
    ├── modules/               # Remote modules downloaded from Git repositories
    │   └── <module_name>/
    │       ├── main.yml
    │       ├── policies/      # Quality policies inherited from the shared module
    │       └── resources/     # Resource templates inherited from the shared module
    ├── policies/              # Local custom validation policies (.ts, .js)
    ├── resources/             # Local custom resource templates (.ts, .js)
    ├── reports/               # Custom report extensions (.ts), formats (.format.ts), and templates (.docx, .xlsx)
    ├── backends/              # Local custom backend storage drivers
    └── ephemeral/             # Metadata of active ephemeral test sandboxes (testform ephemeral)
```

## Components and Files in Project Root

### `.testform.lock.hcl`
- **When it is generated:** During `testform init` when resolving `testform.required_providers`.
- **Purpose:** Records the exact versions and cryptographic SHA-256 hashes (`h1:<base64>`) for each downloaded provider plugin. Ensures deterministic and identical executions across all team workstations and CI/CD pipelines.

---

## Components and Files in `.testform/`

### 1. `cache/backend.json`
- **When it is generated:** During execution of `testform init`.
- **Purpose:** Stores the active configuration and hash of the configured state backend (storage provider, bucket, region, or connection parameters) inside the cache directory.
- **Safety mechanism:** If you change the `backend` block in `main.yml` or supply conflicting `-backend-config` flags, Testform compares the values against `.testform/cache/backend.json` and halts execution to protect state integrity, advising you to run `testform init -reconfigure` or `testform init -migrate-state`.

### 2. `environment`
- **When it is generated:** When managing workspaces via `testform workspace new <name>` or `testform workspace select <name>`.
- **Purpose:** A single-line plain text file storing the name of the currently selected workspace (e.g. `staging` or `production`). If absent, Testform defaults to the `default` workspace.

### 3. `providers/`
- **When it is generated:** During `testform init`, whenever `main.yml` declares entries in `testform.required_providers`.
- **Purpose:** Dedicated directory where Testform downloads and stores executable provider plugins (from Git subpaths, full repos, or npm packages). The dynamic loader (`src/providers/loader.ts`) executes code directly from here.

### 4. `modules/`
- **When it is generated:** During `testform init`, whenever `main.yml` declares module blocks referencing remote sources (`git::https://...`).
- **Purpose:** Holds frozen local copies of remote test modules. This ensures subsequent runs of `testform plan` and `testform apply` remain deterministic and do not depend on continuous internet access or external version control hosts.

> [!NOTE]
> Testform automatically inspects the `policies/` and `resources/` directories inside each downloaded module under `.testform/modules/<name>/`, inheriting enterprise quality gates without manual registration.

### 4. `policies/`
- **When it is used:** Created manually by QA engineers or governance teams.
- **Purpose:** Holds custom validation rules in TypeScript or JavaScript (`.ts`, `.js`, `.mjs`, `.cjs`) registered via the `registerPolicy()` API. Testform auto-discovers and evaluates these policies during `testform validate` and `testform apply`.

### 5. `resources/`
- **When it is used:** Created to define resource connectors or mappings to external systems (Jira, Azure DevOps, TestRail, internal APIs).
- **Purpose:** Contains resource definitions (`registerResource()`) that Testform dynamically compiles and loads at runtime without pre-compilation steps.

### 6. `cache/`
- **When it is generated:** Automatically during `testform init` or incremental parsing.
- **Purpose:** Segregates strictly disposable and regenerable engine artifacts:
  - `backend.json`: Active configuration and hash of the initialized backend.
  - `lock.json`: Provider dependency lock file holding calculated cryptographic checksums.
  - `parser-ast.json`: Incremental Gherkin AST cache (`AstCache`); completely disposable and regenerated automatically.
- **Safety guarantee:** Grouping transient cache files into `cache/` ensures user-authored code in `.testform/policies/`, `.testform/resources/`, and `.testform/reports/` is never accidentally overwritten or lost, while allowing `.testform/cache/` to be cleanly gitignored without complex rules.

### 7. `data.json`
- **When it is generated:** During `testform apply` when the project uses `provider: local`.
- **Purpose:** Persists the simulated mock database for the local provider (created issues, testruns, comments, links, and custom project fields).
- **Git persistence:** Unlike disposable cache files, `data.json` lives directly under `.testform/data.json` so it can be committed to Git when teams want to preserve local test history across contributors or CI/CD pipelines without colliding with throwaway caches.
- **Automatic backward compatibility:** If an existing workspace contains `.testform/cache/data.json`, Testform automatically detects it, migrates it to `.testform/data.json`, and continues execution seamlessly.

### 8. `reports/`
- **When it is used:** Created to extend the analytical reporting capabilities of `testform report`.
- **Purpose:**
  - **Custom reports:** `<name>.ts` scripts implementing `IReport`.
  - **Custom formats:** `<format>.format.ts` scripts implementing `IReportFormat` (e.g., exporters for Slack, PDF, or XML).
  - **Canonical templates:** `report.docx` or `report.xlsx` placed in this directory are loaded transparently as the default template without requiring the `-template` flag.

### 9. `ephemeral/`
- **When it is generated:** When invoking `testform ephemeral up`.
- **Purpose:** Stores session IDs, port allocations, and metadata for temporary QA sandboxes deployed in CI/CD branches, allowing inspection with `testform ephemeral list` and teardown via `testform ephemeral down`.

### 10. `backends/`
- **When it is used:** To store local custom state backend drivers (`.ts` / `.js`) implementing the `IBackend` interface.

## Global User Directory (`~/.testform.d/`)

At the developer machine or CI/CD worker level, Testform maintains a global configuration independent of individual project repositories:

- **Linux / macOS:** `~/.testform.d/`
- **Windows:** `C:\Users\<username>\.testform.d\`

### File `credentials.json`
- **When it is generated:** When running `testform login <hostname>` (e.g., `testform login github.com`).
- **When it is modified:** When running `testform logout <hostname>`.
- **Purpose:** Securely stores provider authentication tokens (e.g., GitHub or GitLab Personal Access Tokens) so the CLI can authenticate against remote APIs without requiring manual environment variables in every shell session:

```json
{
  "hosts": {
    "github.com": {
      "token": "ghp_xxxxxxxxxxxxxxxxxxxx"
    }
  }
}
```

## `.gitignore` Configuration

What you ignore in Git depends on whether you use a remote provider (`github` / `gitlab`) or `provider: local`, and whether you store custom extensions inside `.testform/`:

### Scenario A: Remote provider (`github`, `gitlab`) or ephemeral `provider: local`

Artifacts generated by `testform init` and transient caches should not be committed:

```text
# Testform generated directories and caches
.testform/cache/
.testform/providers/
.testform/modules/
.testform/ephemeral/
.testform/environment

# Binary plan files, locks, and state backups
*.tfplan
*.backup
testform.state.lock

# If using provider: local ephemerally (without versioning state or local database),
# also uncomment:
# testform.state
# .testform/data.json
```

> [!NOTE]
> The `.testform/policies/`, `.testform/resources/`, `.testform/reports/`, and `.testform/backends/` folders contain user-authored code and templates, so they **should be committed to Git** when used.

### Scenario B: `provider: local` with Git-versioned state (`backend: local`)

If you choose to commit `testform.state` in Git while using `provider: local`, **you should also commit `.testform/data.json`**:

```text
# Engine disposable caches
.testform/cache/
.testform/providers/
.testform/modules/
.testform/ephemeral/
.testform/environment
testform.state.lock

# Files to commit in Git to preserve local mock database and state ledger:
# - testform.state
# - .testform/data.json
```

> [!CAUTION]
> If you commit `testform.state` to Git while ignoring `.testform/data.json`, cloning the repository on another machine and running `testform plan`, `testform apply`, or `testform refresh` (which refresh by default) will fail to find the simulated issues in `data.json`, **prune those resources from `testform.state`**, and recreate them from `#1` (with new timestamps and without prior comments). Your `.feature` files and `main.yml` remain safe, but `data.json` and state ledger continuity will reset.

> [!WARNING]
> Never commit or push `~/.testform.d/credentials.json` to a shared repository, as it contains sensitive API tokens.

## Regeneration and Recovery

If the `.testform/` directory is accidentally deleted or you clone the repository onto a new machine:

1. Run `testform init`.
2. Testform automatically re-creates the base directory structure, regenerates `.testform/cache/backend.json`, and re-downloads all declared modules into `.testform/modules/`.
3. If your project was using a workspace other than `default`, switch to it using `testform workspace select <name>`.
4. If using `provider: local` without committing `.testform/data.json`, run `testform apply` to rebuild the local database and `testform.state` from your `.feature` files.
