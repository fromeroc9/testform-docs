title: "Declarative Resources"

Testform defines four fundamental declarative resource primitives to model your end-to-end quality engineering strategy: `testcase`, `testrun`, `testplan`, and `bug`.

## 1. The `testcase` Resource

The `testcase` resource represents an isolated test specification. In Testform, **each `Scenario` inside a `.case.feature` file represents an independent test case**.

- **Standard Location:** `tests/features/*.case.feature`
- **Identity Tag Placement:** Directly above the `Scenario:` with `@tc-*` prefix (e.g. `@tc-cancel-001` or `@tc-cancel-order`).
- **Uniqueness Scope:** Unique within that `.case.feature` file. Resolved as `path/to/file.case.feature.@tc-cancel-001`.
- **Lifecycle:** `draft` -> `active` -> `deprecated` -> `archived`

### Multi-Testcase Feature File Example

```gherkin
Feature: Cancel Pending Purchase Orders
  As a customer with a pending shipment order
  I want to cancel my purchase order from the dashboard
  In order to receive an immediate refund

  Background:
    * field automate = apply

  @high @tc-cancel-001
  Scenario: Cancellation before product fulfillment
    Given order "ORD-9912" is in "Pending" status
    When the customer clicks "Cancel Order"
    And confirms reason "Changed mind"
    Then the order status updates to "Cancelled"
    And a full refund request is submitted

  @medium @tc-cancel-002
  Scenario: Cancellation attempt on already shipped order
    Given order "ORD-8810" is in "Shipped" status
    When the customer clicks "Cancel Order"
    Then the system displays warning "Shipped orders cannot be cancelled"
```

## 2. The `testrun` Resource

The `testrun` resource captures an immutable historical execution of a test set against a specific build or commit.

- **Standard Location:** `tests/runs/*.run.feature`
- **Identity Tag Placement:** Above the `Feature:` with `@tr-*` prefix (e.g. `@tr-regression-build-412`). **1 `.run.feature` file = 1 complete execution run**.
- **Uniqueness Scope:** Globally unique across the entire repository.
- **Internal Structure:** Uses `Rule:` blocks targeting `.case.feature` files and `Scenario:` selectors matching included test cases.

### Example

```gherkin
@tr-regression-build-412 @high
Feature: Regression Test Run Build 412
  Timestamp: 2026-10-21T14:30:00Z
  Triggered By: GitHub Actions (#8912)

  Background:
    * field description = "Critical purchase flow validation"

  Rule: orders.case.feature

  Scenario: @tc-cancel-001
    * set status = passed

  Rule: auth.case.feature

  Scenario: @tc-login-001
    * set status = failed
```

### Rollup Verdict Engine

Testform automatically determines the overall execution outcome (`status`) of each `testrun` by evaluating all individual child test cases (`testcases`). This calculation follows Cucumber's Gherkin severity precedence plus legacy QA blocking rules:

1. **`failed` (Highest Precedence):** If at least one testcase has failed assertions/errors, the entire `testrun` is `failed`.
2. **`ambiguous`:** If none failed, but at least one step matched multiple step definitions, the `testrun` is `ambiguous`.
3. **`undefined`:** If none are `failed`/`ambiguous`, but at least one Gherkin step lacks a step definition, the `testrun` is `undefined`.
4. **`blocked`:** If none of the above apply, but at least one case is `blocked`, the `testrun` is `blocked`.
5. **`pending`:** If any case remains `pending` (or if the suite contains zero cases), the status is `pending`.
6. **`skipped`:** If all cases are either `skipped` or `passed` with at least one `skipped`, the `testrun` is `skipped`.
7. **`passed` (Complete Consensus):** Conferred only when **100% of child test cases** have succeeded with status `passed`.

### Compact Ledger Representation (`testform.state`)

To minimize state file footprint and ensure universal compatibility across providers (Local, GitHub, Jira, GitLab), `testrun` resources persist their executions as a clean, lightweight key-value dictionary:

```json
{
  "address": "tests/runs/regression.run.feature.@tr-regression-build-412",
  "type": "github_testrun",
  "status": "failed",
  "attributes": {
    "title": "Regression Test Run Build 412",
    "status": "failed",
    "testcases": {
      "tests/features/orders.case.feature.@tc-cancel-001": "passed",
      "tests/features/auth.case.feature.@tc-login-001": "failed"
    },
    "metadata": {}
  }
}
```

- **`testcases`**: Compact key-value mapping of `{ [case_canonical_address]: status }`.
- **`metadata`**: Extensible object reserved for providers to record auxiliary execution metadata (build IDs, CI links) without polluting core state.
- **Zero Comment Spam:** Legacy per-testcase issue comments have been replaced by a dynamic, interactive checklist inside the main Issue body, eliminating notification noise and boosting CLI performance.

## 3. The `testplan` Resource

The `testplan` resource models certification matrices, coverage thresholds, and milestone release readiness.

- **Standard Location:** `tests/plans/*.plan.feature`
- **Identity Tag Placement:** Above the `Feature:` with `@tp-*` prefix (e.g. `@tp-release-v250`). **1 `.plan.feature` file = 1 complete certification plan**.
- **Uniqueness Scope:** Globally unique across the entire repository.
- **Internal Structure:** Uses `Rule:` blocks binding referenced runs (`*.run.feature`). Must not contain explicit `Scenario` blocks.

### Example

```gherkin
@tp-release-v250 @high
Feature: Release v2.5.0 Certification Matrix
  Objective: Validate authentication and billing flows prior to production deployment.

  Background:
    * field description = "Release v2.5.0 QA Sign-off"

  Rule: smoke.run.feature

  Rule: regression.run.feature
```

### Hierarchical Certification Verdict

Just as a `testrun` evaluates its test cases, a `testplan` calculates its overall status by hierarchically aggregating the rollup statuses of all linked `testrun` suites:

- Following the same severity order (`failed` > `ambiguous` > `undefined` > `blocked` > `pending` > `skipped` > `passed`), any unresolved child run surfaces directly on the `testplan` verdict.
- If no run has higher-severity issues and any run remains `pending`, the plan verdict stays **`pending`**.
- Only when **all** referenced `testrun` suites reach `passed`, the `testplan` transitions to **`passed`**.

### State Ledger Representation (`testform.state`)

```json
{
  "address": "tests/plans/release.plan.feature.@tp-release-v250",
  "type": "github_testplan",
  "status": "failed",
  "attributes": {
    "title": "Release v2.5.0 Certification Matrix",
    "status": "failed",
    "testruns": {
      "tests/runs/smoke.run.feature.@tr-smoke-412": "passed",
      "tests/runs/regression.run.feature.@tr-regression-build-412": "failed"
    },
    "metadata": {}
  }
}
```

## 4. The `bug` Resource

The `bug` resource models defect tracking, execution failures, and issue resolutions linked directly to test runs and test cases.

- **Standard Location:** `tests/bugs/*.bug.feature` (configurable in `main.yml` via `resources.bug.directory`).
- **Identity Tag Placement:** Directly above each `Scenario:` with `@bg-*` prefix (e.g. `@bg-1` or `@bg-checkout-500`).
- **Uniqueness Scope:** Unique within that bug specification file.
- **Test Run Linkage:** The `Feature:` line points to the relative path of the `testrun` file where the defects were detected (e.g. `Feature: testruns/sprint42.run.feature`).
- **Internal Structure:** Each `Scenario:` represents an individual defect with declarative traceability statements:
  - `* set target = <testcase>`: Affected test case (`@tc-*` or canonical address).
  - `* set status = <status>`: Defect resolution status (`open`, `in_progress`, `resolved`, `reopened`, `discarded`, `duplicate`). Also accepts execution aliases (`failed`, `pending`, `passed`).
  - `* set trace = <stack>`: Error message or stack trace description.
  - `* set attach = <file>` *(or `* set evidence = ...`)*: Physical path or JSON array of attachment/evidence files (screenshots, recordings, logs, or reports).
  - Custom fields (`* set <field> = <value>`): Additional attributes defined in `main.yml` (`resources.bug.fields`).

### Attachment Governance Rules (`set attach` / `set evidence`)

To ensure semantic consistency across Test-as-Code specifications, the engine enforces strict scope rules:

| Resource | Background Scope | Scenario / Rule Scope | Engine Governance |
| :--- | :--- | :--- | :--- |
| **`testcase`** | ✔ Allowed | ✔ Allowed | Shared attachments for the full feature story or specific to individual scenarios. |
| **`testrun`** | ✔ Allowed | ✔ Allowed | Run-level artifacts or specific scenario execution evidence. |
| **`testplan`** | ✔ Allowed | ✖ Prohibited | Only valid in `Background` (plans coordinate runs and do not declare explicit scenarios). |
| **`bug`** | ✖ **Strictly Prohibited** | ✔ Allowed | Defect attachments belong exclusively to the specific failure scenario. |

### Example

```gherkin
@bug
Feature: testruns/sprint42_regression.run.feature

  @bg-1
  Scenario: Error 500 when processing international credit card payment
    * set target = tests/features/checkout.case.feature.@tc-pay-01
    * set status = open
    * set trace = PaymentGatewayException: Timeout waiting for gateway ACK in 30000ms
    * set evidence = evidence/checkout_timeout.png
    * set severity = critical
    * set priority = high

  @bg-2
  Scenario: Confirm order button stays disabled after retry
    * set target = tests/features/checkout.case.feature.@tc-pay-02
    * set status = resolved
    * set evidence = evidence/retry_fixed.png
```

### Defect Lifecycle Statuses

| Status | Meaning | CLI Terminal Display |
| :--- | :--- | :--- |
| **`open`** *(or `failed`, `new`)* | Active unresolved defect | <span style="color:#fa5252">● open</span> |
| **`in_progress`** *(or `pending`)* | Investigation, fix, or retest in progress | <span style="color:#fab005">⧖ in progress</span> |
| **`resolved`** *(or `passed`, `closed`)* | Verified and closed defect | <span style="color:#12b886">✔ resolved</span> |
| **`reopened`** | Previously resolved bug that failed retest | <span style="color:#fd7e14">↻ reopened</span> |
| **`discarded`** *(or `wont_fix`)* | Rejected, not reproducible, or by design | <span style="color:#868e96">⊘ discarded</span> |
| **`duplicate`** | Redundant report of an existing defect | <span style="color:#be4bdb">⧉ duplicate</span> |

### Ledger State Structure (`testform.state`)

```json
{
  "address": "tests/bugs/sprint42.bug.feature.@bg-1",
  "type": "bug",
  "status": "open",
  "attributes": {
    "title": "Error 500 when processing international credit card payment",
    "status": "open",
    "testcase": "tests/features/checkout.case.feature.@tc-pay-01",
    "testrun": "testruns/sprint42_regression.run.feature",
    "trace": "PaymentGatewayException: Timeout waiting for gateway ACK in 30000ms",
    "evidence": ["evidence/checkout_timeout.png"],
    "metadata": {
      "severity": "critical",
      "priority": "high"
    }
  }
}
```

## Resource Comparison Matrix

| Resource | File Scope | Identity Tag Placement | Uniqueness | Internal Structure |
| :--- | :--- | :--- | :--- | :--- |
| **`testcase`** | 1 file = N test cases | Above each `Scenario:` (`@tc-*`) | Unique within file | Isolated `Scenario` blocks with `Given`, `When`, `Then` |
| **`testrun`** | 1 file = 1 test run | Above the `Feature:` (`@tr-*`) | Global across repo | `Rule: file.case.feature` + `Scenario: @tc-*` |
| **`testplan`** | 1 file = 1 test plan | Above the `Feature:` (`@tp-*`) | Global across repo | `Rule: file.run.feature` (testrun coordination) |
| **`bug`** | 1 file = N defects | Above each `Scenario:` (`@bg-*`) | Unique within file | `Scenario` with `target`, `status`, `trace`, `evidence` |

 Custom Resources

Beyond native resources (`github_testcase`, `github_testrun`, `github_testplan`), Testform allows defining **custom resource templates** to map Gherkin scenarios to external APIs (Jira, Zephyr, Azure DevOps, or proprietary QA backends).

### Auto-Discovery by Convention

Testform automatically scans and registers template definitions from:
- `.testform/resources/*.js` (or `./resources/*.js`).
- Shared modules: `.testform/modules/**/resources/*.js`.

### Custom Resource Template Example

```javascript
// .testform/resources/jira-testcase.js
module.exports = {
  type: 'jira_testcase',
  fields: [
    { name: 'summary', value: (scenario) => scenario.name },
    { name: 'description', value: (scenario) => scenario.description || '' },
    { name: 'priority', value: (scenario) => scenario.custom?.fields?.priority || 'Medium' }
  ],
  comments: (scenario, context) => [
    {
      identity: scenario.custom?.identity,
      status: scenario.custom?.fields?.status || 'passed',
      body: `Automated execution report (build #${context?.buildId || 'local'})`,
      title: scenario.name
    }
  ]
};
```
