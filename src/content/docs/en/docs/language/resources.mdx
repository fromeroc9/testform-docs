# Resources (Declarative Resources & Customization)

In Testform, **Resources** are the primary building block of your test suites. While in Terraform a resource models a cloud infrastructure component (an EC2 instance, an S3 bucket), in Testform a resource models a **managed BDD test specification or execution**.

:::note
**BDD as Code:** In Testform, tests live in human-readable Gherkin files (`.feature`), never in YAML blocks. The internal `resource.ts` engine automatically maps BDD scenarios to remote provider APIs (GitHub, Jira, TestRail, etc.).
:::

---

## Canonical Resource Types

Testform includes built-in declarative templates for quality management entities:

| Resource | Purpose | Format / Location |
|---|---|---|
| **`github_testcase`** | Individual test specification | `Scenario:` in `*.case.feature` |
| **`github_testrun`** | Immutable test execution tracking | `*.run.feature` |
| **`github_testplan`** | Orchestration and execution schedule | `*.plan.feature` |
| **Custom Resources** | Custom resources for Jira, TestRail, etc. | Registered via `registerResource()` |

---

## 1. Field Extension via YAML (Declarative Configuration)

When you want to add calculated fields or extra metadata to standard canonical resources (`testcase`, `testrun`, `testplan`), you can extend them directly in your YAML configuration file under the `resource` block without writing TypeScript or rewriting step generators:

```yaml
# main.yml
resource:
  testcase:
    fields:
      severity: "${custom.fields.severity || 'Normal'}"
      jira_component: "${custom.fields.component || 'Core'}"
      team_owner: "QA-Core"
```

Declared fields automatically merge with the resource's native fields at runtime.

## 2. Modifying Declared Resources (`registerResource`)

Built-in resources (`github_testcase`, `github_testrun`, etc.) **are not closed black boxes**. Any team can modify or override attributes, lifecycle orchestration hooks, or state persistence using `registerResource()`.

User definitions automatically take precedence over system templates, preserving unmentioned fields:

<Tabs>
<TabItem label="TypeScript">
```typescript
import { registerResource } from '@fromeroc9/testform@beta';

// Customize the built-in github_testcase resource
registerResource({
    type: 'github_testcase',
    attributes: (s) => ({
        // Prefix test title with team tag
        title: `[QA-CORE] ${s.name}`,
        
        // Custom Markdown body format
        body: `## 📋 Test Case: ${s.name}\n\n### Steps:\n` + 
              s.steps.map(step => `- **${step.keyword}** ${step.text}`).join('\n'),

        // Custom automated labels
        labels: [...new Set(['automated', ...(s.tags || []).map(t => t.replace('@', ''))])] 
    }),
    lifecycle: {
        afterCreate: async ({ id, attributes, provider }) => {
            console.log(`Resource #${id} created in ${provider.name}`);
        }
    }
});
```
</TabItem>

## 3. Registering Custom Resources & Providers

To connect Testform to external platforms (Jira, TestRail, Zephyr, databases, or proprietary domain resources such as a `pokedex`), register new resources mapping their canonical attributes to the provider's resource handlers:

```typescript
import { registerResource } from '@fromeroc9/testform@beta';

registerResource({
    type: 'register-pokemon',
    attributes: (s) => ({
        nombre: s.name,
        tipo: s.custom?.fields?.tipo ?? 'Eléctrico',
        nivel: s.custom?.fields?.nivel ?? 25,
        foto: s.custom?.fields?.foto ?? 'https://img.pokemondb.net/sprites/home/normal/pikachu.png'
    }),
    lifecycle: {
        beforeCreate: async ({ attributes }) => {
            if (attributes.nivel < 1 || attributes.nivel > 100) {
                throw new Error('Pokémon level must be between 1 and 100');
            }
        },
        afterCreate: async ({ id, attributes, provider }) => {
            // Direct invocation of custom actions exposed on the live provider instance
            if (provider.subirFotoPokemon) {
                await provider.subirFotoPokemon(id, attributes.foto);
            }
        }
    },
    state: {
        region: () => 'Kanto'
    }
});
```

## 4. Canonical Resource Addresses

Just as Terraform uniquely identifies resources (e.g., `aws_instance.web`), Testform addresses resources using **pure dot notation**:

```text
<relative_file_path>.<identifier_tag>
```

Examples:
- `features/auth/login.case.feature.@tc-001`
- `features/checkout/payment.case.feature.@tc-stripe`

---

## 5. Resource Reconciliation

During `testform plan`, Testform compares declared BDD scenarios against the records in `testform.state`:

- **`+ create`**: A new test scenario has been added to the codebase.
- **`~ update`**: Steps, tags, or variables in an existing scenario changed.
- **`- destroy`**: A previously recorded scenario was deleted.
