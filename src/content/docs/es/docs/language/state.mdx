---
title: "Gestión y Ledger de Estado"
---

El **Estado (`testform.state`)** es el registro autoritativo que mapea la intención declarativa de tus archivos de prueba contra los resultados reales y atributos físicos de cada ejecución.

Al igual que en Terraform el archivo de estado registra los IDs de las instancias de nube creadas, en Testform el estado guarda los identificadores remotos de las pruebas, los hashes de contenido para detección de cambios, el estado de ejecución (`passed`, `failed`, `skipped`) y los valores de salida (`outputs`).

---

### Estructura y Paridad con Terraform (State Schema v2)

A diferencia de enfoques heredados monolíticos, el estado desacopla la **identidad lógica (`address`)** de la **ubicación en disco (`path`)**:

| Campo | Tipo | Descripción |
| :--- | :--- | :--- |
| `address` | `string` | Dirección canónica lógica: `[namespace.]basename.[scope].feature.[@tag]`. Si mueves un archivo de carpeta, el `address` permanece inmutable y Testform preserva la sincronización remota sin recrear recursos. |
| `physicalAddress` | `string` | Dirección física exacta en disco: `path + tag` para `testcase` y `bug`, o `path` (+ `tag` opcional) para `testrun` y `testplan`. |
| `path` | `string` | Ruta física del archivo relativa al scaffold o proyecto (ej. `tests/features/cart.case.feature`). |
| `tag` | `string` | *(Opcional en runs y plans, obligatorio en cases y bugs)* Identificador atómico (`@tc-01`, `@tr-01`, `@tp-01`, `@bg-01`). |
| `namespace` | `string` | *(Opcional)* Espacio de nombres lógico declarado con `@ns(nombre)`. |
| `type` | `string` | Tipo canónico de recurso (`testcase`, `testrun`, `testplan`, `bug`). |
| `attributes` | `object` | Diccionario de metadatos de sincronización: `localHash`, `remoteId`, `issueNumber`, `title`, labels y campos dinámicos. |
| `lastApplied` | `string` | Timestamp ISO 8601 de la última aplicación exitosa. |

### Arquitectura Dual: Dirección Lógica vs Dirección Física

Testform opera de manera bidireccional y transparente con ambas identidades en todos los comandos CLI (`-target`, `show`, `state`, etc.):

1. **Para `testcase` y `bug`**:
   * **Dirección Lógica:** `[namespace.]basename.@tag` (ej. `cart.case.feature.@tc-01` o `checkout.cart.case.feature.@tc-01`).
   * **Dirección Física:** `path + tag` (ej. `folder1/cart.case.feature.@tc-01`).
   * *El `tag` es obligatorio* porque un solo archivo `.case.feature` o `.bug.feature` contiene múltiples escenarios.

2. **Para `testrun` y `testplan`**:
   * **Dirección Lógica:** `[namespace.]basename.[@tag]` (ej. `smoke.run.feature.@tr-01` o simplemente `smoke.run.feature`).
   * **Dirección Física:** `path` o `path + tag` (ej. `folder1/smoke.run.feature` o `folder1/smoke.run.feature.@tr-01`).
   * *El `tag` es opcional* porque 1 archivo representa 1 ejecución o plan completo.

### Desempate Automático ante Archivos Homónimos (Cero Conflictos)

¿Qué sucede si existen dos archivos con el mismo nombre en diferentes carpetas (ej. `folder1/a.case.feature` y `folder2/a.case.feature`)?

1. **Si tienen `@ns(...)`:**
   * Archivo 1 con `@ns(checkout)` ➔ `checkout.a.case.feature.@tc-01`
   * Archivo 2 con `@ns(billing)` ➔ `billing.a.case.feature.@tc-01`
   * Ambas direcciones lógicas son únicas. Cero conflicto.
2. **Si NO tienen `@ns(...)`:**
   * El motor detecta la duplicidad de basenames entre carpetas y **adopta automáticamente la dirección física relativa** (`folder1/a.case.feature.@tc-01` vs `folder2/a.case.feature.@tc-01`).
   * **Garantía de cero colisiones** en el estado y en el reporte.

### Tabla Comparativa: El Viejo Identity Monolítico vs el Modelo Dual State v2

| Característica | El Viejo `identity` (Monolítico) | El Nuevo Modelo Dual (State Schema v2) |
| :--- | :--- | :--- |
| **Estructura** | Un único string plano gigante:<br/>`tests/features/folder1/a.case.feature.@tc-01` | Estructurado y desacoplado:<br/>`address`: `[ns.]basename.@tag`<br/>`path`: `folder1/a.case.feature`<br/>`tag`: `@tc-01`<br/>`physicalAddress`: `folder1/a.case.feature.@tc-01` |
| **Archivos con igual nombre** (`folder1/a` vs `folder2/a`) | No colisionaban porque el string incluía la ruta física completa. | **No colisionan:** Si no hay `@ns`, adopta automáticamente la ruta física (`folder1/a...` vs `folder2/a...`), **igual de seguro que el viejo**. |
| **Al mover un archivo de carpeta** | **Catastrófico:** El string `identity` cambiaba, Testform creía que era un caso nuevo, **borraba el Issue en GitHub/Jira y creaba uno nuevo**, perdiendo todo el historial. | **Seguro:** Si tiene `@ns` o nombre único, el `address` permanece inmutable. Testform solo actualiza el `path` en el estado sin tocar el Issue remoto. |
| **Tag en `testrun` y `testplan`** | Se pegaba obligatoriamente al final del path (`path.@tr-1`) o quedaba como path crudo. | **Opcional y limpio:** Puedes usar `folder1/a.run.feature.@tr-01` o simplemente `folder1/a.run.feature`. |
| **Búsqueda y targeting (`-target`)** | Forzado a buscar por coincidencia de subcadenas o el path completo. | **Polimórfico:** Puedes targetear por tag (`@tc-01`), por dirección lógica (`a.case.feature.@tc-01`), o por ruta física (`folder1/a.case.feature.@tc-01`). |
| **En los Testruns (`Rule: ...`)** | Podías referenciar por path o nombre de feature. | Acepta **path físico** (`folder1/a.case.feature`), **namespace** (`checkout.a.case.feature`) o **nombre base** (`a.case.feature`). |

### Atributos Clave de Recursos en el Estado

| Campo | Recurso(s) | Descripción |
| :--- | :--- | :--- |
| `status` | `testcase`, `testrun`, `testplan` | Resultado de ejecución o veredicto consolidado (*Rollup Verdict*). |
| `testcases` | `testrun` | Mapa clave-valor `{ [identidad_caso]: estado }` de todos los casos ejecutados. |
| `testruns` | `testplan` | Mapa clave-valor `{ [identidad_run]: estado }` de las suites agrupadas en el plan. |
| `metadata` | `testrun`, `testplan` | Objeto extensible para atributos arbitrarios del proveedor (builds, CI/CD, tags remotos). |

## Bloqueo de Estado Concurrente (`testform.state.lock`)

Para prevenir condiciones de carrera y corrupción cuando múltiples miembros del equipo o pipelines de CI/CD ejecutan pruebas simultáneamente, Testform implementa **bloqueo atómico de estado**:

1. Antes de iniciar cualquier plan o aplicación, Testform adquiere un lock (`testform.state.lock`).
2. El archivo de bloqueo registra el ID del proceso (PID), usuario, hostname y timestamp.
3. Si otro proceso intenta acceder al estado mientras está bloqueado:
```text
[ERROR] Error acquiring the state lock:
  Lock Info:
    ID:        a9b8c7-lock
    Path:      testform.state
    Operation: OperationTypeApply
    Who:       runner-1@ci-node-4
    Created:   2026-10-24 17:15:00 UTC
```

## Detección de Deriva (Drift Detection)

Durante la fase de reconciliación (`testform refresh` o `testform plan`):
- Testform calcula el checksum criptográfico del código actual de cada escenario.
- Si el código local o los resultados remotos han variado respecto a lo grabado en el estado, se genera un plan de actualización (`~ update`).
- Las modificaciones no intencionadas o pruebas que fallan de manera silenciosa son detectadas de inmediato.
