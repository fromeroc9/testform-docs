# Resources (Recursos Declarativos y Personalización)

En Testform, los **Recursos** son el bloque de construcción fundamental del testing. Mientras que en Terraform un recurso modela un componente de infraestructura (una instancia EC2, un bucket S3), en Testform un recurso modela una **especificación BDD de prueba o una ejecución** con ciclo de vida gestionado.

:::note
**BDD as Code:** En Testform las pruebas viven en archivos Gherkin (`.feature`), no en bloques YAML. El motor interno de `resource.ts` traduce automáticamente los escenarios a los objetos de las APIs remotas de los proveedores.
:::

---

## Contrato de Recursos: `attributes` vs `state`

Testform desacopla el contrato de cada recurso en dos fases complementarias, garantizando un motor 100% agnóstico y extensible (sea un issue de GitHub/GitLab, un contenedor Docker, una máquina virtual o cualquier entidad):

1. **`attributes` (Estado Deseado Declarativo):**
   Representa la intención declarativa que el usuario define y que se envía a las APIs del proveedor remoto durante `apply`:
   - En recursos canónicos de testing: `title`, `body`, `labels`, `assignees`, `milestone`, `state` y **`metadata`** (diccionario unificado de campos personalizados como `priority`, `severity`, `component`, etc.).
   - En recursos personalizados: cualquier atributo que requiera la API destino (ej. `image`, `ports`, `instance_type`, etc.).

2. **`state` (Datos de Ejecución y Estado Operacional Local):**
   **El autor del recurso define qué datos se calculan y guardan en el ledger local (`testform.state`)**. A diferencia de `attributes` (que viaja a la API remota), `state` almacena información observada, métricas o resultados de runtime que se monitorean localmente:
   - **En recursos personalizados:** El usuario define libremente qué registrar en su plantilla `registerResource({ state: { ... } })` (por ejemplo, `container_id`, `ip_asignada`, `tiempo_arranque`).
   - **En los recursos canónicos de pruebas (`testcase`, `testrun`, `bug`):** Testform incluye por defecto funciones que extraen los datos de ejecución producidos por los test runners o por las instrucciones `* set` del escenario (`status`, `duration`, `trace`, `attach`, mapas de `testcases` / `testruns`).

No existe duplicidad entre `custom_fields` y `metadata`; `metadata` es el estándar unificado dentro de `attributes` para campos personalizados, mientras que `state` almacena los datos de operación y ejecución definidos en la plantilla.

## Tipos Canónicos de Recursos

Testform define internamente plantillas declarativas para los recursos de gestión de calidad:

| Recurso | Propósito | Formato / Ubicación |
|---|---|---|
| **`testcase`** | Especificación unitaria de prueba individual | `Scenario:` en archivos `*.case.feature` |
| **`testrun`** | Ejecución inmutable de pruebas contra un build | `*.run.feature` |
| **`testplan`** | Plan de orquestación y alcance de pruebas | `*.plan.feature` |
| **`bug`** | Reporte estructurado y trazabilidad de defectos | `*.bug.feature` |
| **Custom Resources** | Recursos personalizados para Jira, TestRail, etc. | Definidos mediante `registerResource()` |

## 1. Extensión de Campos en YAML (Configuración Declarativa)

Cuando deseas agregar campos calculados o metadatos adicionales a los recursos canónicos (`testcase`, `testrun`, `testplan`), puedes extenderlos directamente en el bloque `resource` de tu archivo de configuración YAML, sin necesidad de redefinir generadores de pasos ni código TypeScript:

```yaml
# main.yml
resource:
  testcase:
    fields:
      severity: "${custom.fields.severity || 'Normal'}"
      jira_component: "${custom.fields.component || 'Core'}"
      team_owner: "QA-Core"
```

Los campos declarados se fusionan automáticamente con los campos nativos del recurso en tiempo de ejecución.

## 2. Modificación de Recursos ya Declarados por el Usuario (`registerResource`)

Los recursos canónicos (`testcase`, `testrun`, etc.) **no son cajas negras cerradas**. Cualquier equipo puede modificar o sobreescribir los atributos, el ciclo de vida o los datos de estado generados utilizando `registerResource()`.

Las definiciones del usuario toman precedencia automática sobre las plantillas del sistema, preservando los campos no modificados:

<Tabs>
<TabItem label="TypeScript">
```typescript
import { registerResource } from '@fromeroc9/testform@beta';

// Sobreescribir el recurso canónico testcase
registerResource({
    type: 'testcase',
    attributes: (s) => ({
        // Personalizamos el título con un prefijo corporativo
        title: `[QA-CORE] ${s.name}`,
        
        // Formato Markdown personalizado para el cuerpo del Issue
        body: `## Caso de Prueba: ${s.name}\n\n### Pasos a Ejecutar:\n` + 
              s.steps.map(step => `- **${step.keyword}** ${step.text}`).join('\n'),

        // Etiquetas automáticas personalizadas
        labels: [...new Set(['automated', ...(s.tags || []).map(t => t.replace('@', ''))])] 
    }),
    lifecycle: {
        afterCreate: async ({ id, attributes, provider }) => {
            console.log(`Recurso #${id} creado en ${provider.name}`);
        }
    }
});
```

## 3. Registro de Nuevos Recursos y Proveedores Personalizados

Para conectar Testform con plataformas externas (Jira, TestRail, Zephyr, bases de datos o servicios propietarios como una `pokedex`), se registran recursos adicionales asociando sus atributos canónicos con las funciones del proveedor:

```typescript
import { registerResource } from '@fromeroc9/testform@beta';

registerResource({
    type: 'register-pokemon',
    attributes: (s) => ({
        nombre: s.name,
        tipo: s.custom?.fields?.tipo ?? 'Eléctrico',
        nivel: s.custom?.fields?.nivel ?? 25,
        foto: s.custom?.fields?.foto ?? 'https://img.pokemondb.net/sprites/home/normal/pikachu.png'
    }),
    lifecycle: {
        beforeCreate: async ({ attributes }) => {
            if (attributes.nivel < 1 || attributes.nivel > 100) {
                throw new Error('El nivel del Pokémon debe estar entre 1 y 100');
            }
        },
        afterCreate: async ({ id, attributes, provider }) => {
            // Invocación directa del método custom para subir la foto oficial
            if (provider.subirFotoPokemon) {
                await provider.subirFotoPokemon(id, attributes.foto);
            }
        }
    },
    state: {
        region: () => 'Kanto'
    }
});
```

## 4. Direcciones Canónicas de Recursos (Resource Addresses)

Al igual que en Terraform cada recurso posee un identificador universal único (ej. `aws_instance.web`), en Testform cada recurso se direcciona mediante **notación por puntos pura**:

```text
<ruta_archivo_relativa>.<tag_identificador>
```

Ejemplos:
- `features/auth/login.case.feature.@tc-001`
- `features/checkout/payment.case.feature.@tc-stripe`

Estas direcciones son utilizadas por:
- El motor de dependencias `@depends_on("features/auth/login.case.feature.@tc-001")`
- El ledger inmutable de estado `testform.state`
- Comandos CLI como `testform state show <address>` y `testform taint <address>`

## 5. Estado y Conciliación

Durante `testform plan`, el motor compara los recursos declarados en el código BDD con el estado actual registrado en `testform.state`:

- **`+ create`**: Se ha creado un nuevo escenario de prueba.
- **`~ update`**: Se han modificado pasos, tags o variables de un escenario existente.
- **`- destroy`**: Se ha eliminado un escenario del código.
