---
title: "depends_on"
---

El meta-argumento `depends_on` permite definir dependencias explícitas de ejecución entre casos de prueba, garantizando que los requisitos previos se sincronicen y ejecuten en el orden correcto mediante un **Grafo Acíclico Dirigido (DAG)**.

---

## Declaración en Gherkin (`@depends_on`)

Las dependencias se declaran directamente como tag sobre el `Scenario:`, admitiendo tanto notación de array (idéntica a la lista de Terraform) como argumentos separados por comas:

```gherkin
@checkout @e2e
@depends_on(["auth/login.feature.@login_success", "inventory/cart.feature.@add_item"])
Scenario: Finalización exitosa de orden de compra
  Given que el carrito contiene productos seleccionados
  When confirmo los datos de envío y pago
  Then la orden de compra es emitida exitosamente
```

También es válido declarar `@depends_on("auth/login.feature.@login_success", "inventory/cart.feature.@add_item")` o tags `@depends_on(...)` repetidos.

### Sintaxis sin Comillas y Ámbito por Regla

Las referencias directas admiten notación sin comillas obligatorias tanto para IDs locales como etiquetas:

```gherkin
@depends_on(@tc-01)
@depends_on(tc-01)
@depends_on("auth/login.case.feature.@tc-01")
```

---

## Trazabilidad Defecto $\rightarrow$ Testcase en `@bug`

En especificaciones de defectos (`*.bug.feature`), `@depends_on` se utiliza para enlazar automáticamente el bug con el caso de prueba fallido bajo un bloque `Rule:`:

```gherkin
Rule: tests/features/checkout.case.feature

  @bg-01 @depends_on(@tc-01)
  Scenario: Error 500 al procesar pago con tarjeta internacional
    * set status = open
    * set attach = "attachments/bugs/error.png"
    * field severity = @critical
```

El motor resuelve automáticamente el enlace hacia el escenario `@tc-01` definido dentro del archivo `Rule:`, habilitando navegación **Go-to-Definition (F12)** y previsualizaciones **Hover** directas en VS Code. También se admite la forma abreviada `@bg-01 @tc-01`.

> [!CAUTION]
> **Sintaxis deprecada (`* set target`):** Declarar la relación mediante un paso `* set target = ...` o `* set case = ...` dentro de escenarios `@bug` está obsoleto y ya no se recomienda. Utiliza siempre `@depends_on(@tc-*)` (idealmente bajo `Rule: <archivo.case.feature>`) o la forma completa `@depends_on("ruta/archivo.case.feature.@tc-*")`.

---

## Orden de Ejecución Topológico (DAG)

Durante `testform plan` y `testform apply`:
1. Testform construye un grafo acíclico dirigido (**DAG**) de todos los recursos declarados.
2. Aplica el **algoritmo de ordenamiento topológico de Kahn** para determinar la secuencia exacta.
3. Los escenarios padre (`auth/login`) se ejecutan y validan siempre **antes** que los escenarios dependientes (`checkout/order`).

---

## Detección Preventiva de Ciclos Circulares

Si se declara una dependencia circular (ej. $A \rightarrow B \rightarrow A$), Testform aborta inmediatamente en la fase estática de validación sin ejecutar pruebas a ciegas:

```text
[ERROR] Circular dependency detected in DAG:
  auth/login.feature.@login_success -> checkout/order.feature.@checkout -> auth/login.feature.@login_success
```

## Visualización del Grafo: `testform graph`

Puedes generar y visualizar el grafo completo de dependencias en formato DOT:

```bash
testform graph
```
```bash
# Renderizar como imagen con Graphviz:
testform graph | dot -Tpng -o dependencies.png
```
