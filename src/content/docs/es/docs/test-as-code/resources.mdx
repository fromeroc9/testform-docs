title: "Recursos Declarativos"
---


Testform define cuatro tipos de recursos fundamentales para modelar la estrategia de calidad de extremo a extremo: `testcase`, `testrun`, `testplan` y `bug`.

## 1. El Recurso `testcase`

El recurso `testcase` representa una especificacion de prueba individual. En Testform, **cada `Scenario` dentro de un archivo `.case.feature` constituye un caso de prueba independiente**.

- **Ubicacion Estandar:** `tests/features/*.case.feature`
- **Ubicacion de Identidad:** Directamente sobre el `Scenario:` con prefijo `@tc-*` (ejemplo: `@tc-cancel-001` o `@tc-cancel-order`).
- **Nivel de Unicidad:** Unico dentro del mismo archivo `.case.feature`. La direccion completa en el ledger es `ruta/archivo.case.feature.@tc-cancel-001` (o con namespace de provider: `github_testcase.ruta/archivo.case.feature.@tc-cancel-001`).
- **Ciclo de Vida:** `draft` -> `active` -> `deprecated` -> `archived`

### Ejemplo de Archivo con Multiples Casos

```gherkin
Feature: Cancelacion de Pedidos Pendientes
  Como cliente con un pedido pendiente de envio
  Quiero cancelar mi compra desde el panel de ordenes
  Para recibir el reembolso inmediato

  Background:
    * field automate = apply

  @high @tc-cancel-001
  Scenario: Cancelacion antes del empaque del producto
    Given el pedido "ORD-9912" se encuentra en estado "Pendiente"
    When el usuario pulsa "Cancelar Pedido"
    And confirma el motivo "Cambio de opinion"
    Then el estado del pedido cambia a "Cancelado"
    And se emite una solicitud de reembolso por el total de la orden

  @medium @tc-cancel-002
  Scenario: Intento de cancelacion de un pedido ya despachado
    Given el pedido "ORD-8810" se encuentra en estado "Enviado"
    When el usuario pulsa "Cancelar Pedido"
    Then el sistema muestra la alerta "El pedido ya fue despachado y no puede cancelarse"
```

## 2. El Recurso `testrun`

El recurso `testrun` captura la ejecucion historica e inmutable de un conjunto de pruebas contra una version especifica de la aplicacion.

- **Ubicacion Estandar:** `tests/runs/*.run.feature`
- **Ubicacion de Identidad:** Sobre el `Feature:` con prefijo `@tr-*` (ejemplo: `@tr-regression-build-412`). **1 archivo `.run.feature` = 1 ejecucion completa**.
- **Nivel de Unicidad:** Globalmente unico en todo el repositorio.
- **Estructura Interna:** Utiliza bloques `Rule:` para apuntar a archivos `.case.feature` y bloques `Scenario:` para seleccionar los tags de los casos incluidos.

### Ejemplo

```gherkin
@tr-regression-build-412 @high
Feature: Registro de Ejecucion de Regresion Build 412
  Fecha: 2026-10-21T14:30:00Z
  Ejecutor: GitHub Actions (#8912)

  Background:
    * field descripcion = "Validacion de flujos criticos de compras"

  Rule: orders.case.feature

  Scenario: @tc-cancel-001
    * set status = passed

  Rule: auth.case.feature

  Scenario: @tc-login-001
    * set status = failed
```

### Motor de Veredicto Acumulado (*Rollup Verdict*)

Testform calcula de forma totalmente automática el estado consolidado (`status`) de cada `testrun` evaluando los estados individuales de todos los escenarios contenidos (`testcases`). Este cálculo sigue el orden de severidad Gherkin de Cucumber (más soporte para `blocked`):

1. **`failed` (Máxima Prioridad):** Si al menos un caso de prueba falló, el `testrun` se califica automáticamente como `failed`.
2. **`ambiguous`:** Si no hay fallos pero algún caso tiene pasos ambiguos (múltiples definiciones coincidentes), el estado resulta `ambiguous`.
3. **`undefined`:** Si no hay `failed`/`ambiguous` pero existen pasos sin implementación en Cucumber, el estado resulta `undefined`.
4. **`blocked`:** Si no aplica lo anterior pero algún caso permanece en `blocked`, el resultado es `blocked`.
5. **`pending`:** Si al menos un caso permanece en `pending` (o si la suite no tiene casos registrados), el resultado es `pending`.
6. **`skipped`:** Si todos los casos terminaron entre `passed` y `skipped` (con al menos un `skipped`), el resultado es `skipped`.
7. **`passed` (Consenso Total):** Se otorga únicamente si el **100% de los casos de prueba** concluyeron con estado `passed`.

### Persistencia Compacta en el Ledger (`testform.state`)

Para garantizar un tamaño mínimo del archivo de estado y compatibilidad universal entre proveedores (Local, GitHub, Jira, GitLab), el `testrun` persiste sus ejecuciones como un mapa clave-valor ligero:

```json
{
  "address": "tests/runs/regression.run.feature.@tr-regression-build-412",
  "type": "github_testrun",
  "status": "failed",
  "attributes": {
    "title": "Registro de Ejecucion de Regresion Build 412",
    "status": "failed",
    "testcases": {
      "tests/features/orders.case.feature.@tc-cancel-001": "passed",
      "tests/features/auth.case.feature.@tc-login-001": "failed"
    },
    "metadata": {}
  }
}
```

- **`testcases`**: Diccionario normalizado `{ [identificador_caso]: estado }`. Elimina estructuras anidadas pesadas.
- **`metadata`**: Objeto extensible reservado para que cualquier proveedor registre atributos auxiliares específicos sin contaminar la estructura base.
- **Sin comentarios invasivos:** Se sustituyó la creación recursiva de comentarios en issues de GitHub por una lista de verificación interactiva directamente en la descripción del Issue, eliminando ruidos en notificaciones y acelerando el rendimiento del CLI.

## 3. El Recurso `testplan`

El recurso `testplan` modela matrices de certificacion, requisitos de cobertura y alcance de pruebas para un hito o lanzamiento.

- **Ubicacion Estandar:** `tests/plans/*.plan.feature`
- **Ubicacion de Identidad:** Sobre el `Feature:` con prefijo `@tp-*` (ejemplo: `@tp-release-v250`). **1 archivo `.plan.feature` = 1 plan de pruebas completo**.
- **Nivel de Unicidad:** Globalmente unico en todo el repositorio.
- **Estructura Interna:** Utiliza bloques `Rule:` para agrupar las ejecuciones (`*.run.feature`) asociadas al plan. No debe contener bloques `Scenario` explicitos.

### Ejemplo

```gherkin
@tp-release-v250 @high
Feature: Plan de Certificacion Release v2.5.0
  Objetivo: Validar los flujos de autenticacion y facturacion antes del paso a produccion.

  Background:
    * field descripcion = "Release v2.5.0 QA Sign-off"

  Rule: smoke.run.feature

  Rule: regression.run.feature
```

### Veredicto Jerárquico de Certificación

Al igual que el `testrun` evalúa sus casos, el `testplan` calcula su estado acumulando jerárquicamente los estados de todos los `testrun` vinculados:

- Siguiendo exactamente la misma precedencia (`failed` > `ambiguous` > `undefined` > `blocked` > `pending` > `skipped` > `passed`), el estado más severo de los `testrun` vinculados se propaga al veredicto del `testplan`.
- Si ningún `testrun` tiene fallos ni estados bloqueantes pero alguno continúa en `pending`, el plan permanece en **`pending`**.
- Solo cuando la totalidad de las suites `testrun` vinculadas culminan en `passed`, el `testplan` adquiere el estado **`passed`**.

### Estructura en el Estado (`testform.state`)

```json
{
  "address": "tests/plans/release.plan.feature.@tp-release-v250",
  "type": "github_testplan",
  "status": "failed",
  "attributes": {
    "title": "Plan de Certificacion Release v2.5.0",
    "status": "failed",
    "testruns": {
      "tests/runs/smoke.run.feature.@tr-smoke-412": "passed",
      "tests/runs/regression.run.feature.@tr-regression-build-412": "failed"
    },
    "metadata": {}
  }
}
```

## 4. El Recurso `bug`

El recurso `bug` modela la trazabilidad inmutable y el ciclo de vida de los defectos encontrados durante la ejecución de pruebas.

- **Ubicacion Estandar:** `tests/bugs/*.bug.feature` (configurable en `main.yml` bajo `resources.bug.directory`).
- **Ubicacion de Identidad:** Sobre cada `Scenario:` con prefijo `@bg-*` (ejemplo: `@bg-1` o `@bg-checkout-500`).
- **Nivel de Unicidad:** Unico dentro del archivo contenedor de bugs.
- **Relacion con Test Runs:** La linea `Feature:` del archivo apunta a la ruta relativa del `testrun` en el que se originaron o detectaron los defectos (ejemplo: `Feature: testruns/sprint42.run.feature`).
- **Estructura Interna:** Cada `Scenario:` representa un defecto individual con sus sentencias declarativas de trazabilidad:
  - `* set target = <testcase>`: Caso de prueba afectado (`@tc-*` o direccion canonical).
  - `* set status = <estado>`: Estado de resolucion del defecto (`open`, `in_progress`, `resolved`, `reopened`, `discarded`, `duplicate`). Tambien acepta los equivalentes de ejecucion (`failed`, `pending`, `passed`).
  - `* set trace = <stack>`: Mensaje o traza del error detectado.
  - `* set attach = <archivo>` *(o `* set evidence = ...`)*: Ruta física o lista JSON de adjuntos/evidencias (captura de pantalla, grabaciones de video, logs o reportes).
  - Campos personalizados (`* set <campo> = <valor>`): Metadatos adicionales definidos en `main.yml` (`resources.bug.fields`).

### Reglas de Gobernanza de Adjuntos (`set attach` / `set evidence`)

Para garantizar coherencia semántica en la arquitectura Test-as-Code, el motor impone reglas estrictas de ámbito:

| Recurso | Nivel Background | Nivel Scenario / Rule | Comportamiento del Motor |
| :--- | :--- | :--- | :--- |
| **`testcase`** | ✔ Permitido | ✔ Permitido | Permite adjuntos compartidos para toda la historia/feature o específicos por caso. |
| **`testrun`** | ✔ Permitido | ✔ Permitido | Permite artefactos generales de la corrida o evidencias específicas por escenario ejecutado. |
| **`testplan`** | ✔ Permitido | ✖ Prohibido | Solo aplicable en `Background` (los planes no contienen escenarios individuales). |
| **`bug`** | ✖ **Estrictamente prohibido** | ✔ Permitido | Los adjuntos pertenecen exclusivamente a la evidencia particular del defecto en el `Scenario`. |

### Ejemplo

```gherkin
@bug
Feature: testruns/sprint42_regression.run.feature

  @bg-1
  Scenario: Error 500 al procesar pago con tarjeta internacional
    * set target = tests/features/checkout.case.feature.@tc-pay-01
    * set status = open
    * set trace = PaymentGatewayException: Timeout waiting for gateway ACK in 30000ms
    * set evidence = evidence/checkout_timeout.png
    * set severity = critical
    * set priority = high

  @bg-2
  Scenario: Boton de confirmar pedido queda deshabilitado tras reintento
    * set target = tests/features/checkout.case.feature.@tc-pay-02
    * set status = resolved
    * set evidence = evidence/retry_fixed.png
```

### Ciclo de Vida de los Defectos

| Estado | Significado | Representacion CLI |
| :--- | :--- | :--- |
| **`open`** *(o `failed`, `new`)* | Defecto activo y no resuelto | <span style="color:#fa5252">● open</span> |
| **`in_progress`** *(o `pending`)* | Defecto en investigacion, reparacion o retest | <span style="color:#fab005">⧖ in progress</span> |
| **`resolved`** *(o `passed`, `closed`)* | Defecto verificado y corregido | <span style="color:#12b886">✔ resolved</span> |
| **`reopened`** | Defecto previamente resuelto que volvio a manifestarse | <span style="color:#fd7e14">↻ reopened</span> |
| **`discarded`** *(o `wont_fix`)* | Defecto rechazado, no reproducible o por diseño | <span style="color:#868e96">⊘ discarded</span> |
| **`duplicate`** | Defecto reportado que duplica otro caso existente | <span style="color:#be4bdb">⧉ duplicate</span> |

### Estructura en el Estado (`testform.state`)

```json
{
  "address": "tests/bugs/sprint42.bug.feature.@bg-1",
  "type": "bug",
  "status": "open",
  "attributes": {
    "title": "Error 500 al procesar pago con tarjeta internacional",
    "status": "open",
    "testcase": "tests/features/checkout.case.feature.@tc-pay-01",
    "testrun": "testruns/sprint42_regression.run.feature",
    "trace": "PaymentGatewayException: Timeout waiting for gateway ACK in 30000ms",
    "evidence": ["evidence/checkout_timeout.png"],
    "metadata": {
      "severity": "critical",
      "priority": "high"
    }
  }
}
```

## Matriz Comparativa de Recursos

| Recurso | Alcance | Ubicacion de Identidad | Unicidad | Estructura Interna |
| :--- | :--- | :--- | :--- | :--- |
| **`testcase`** | 1 archivo = N casos | Sobre cada `Scenario:` (`@tc-*`) | Unica en el archivo | `Scenario` individuales con `Given`, `When`, `Then` |
| **`testrun`** | 1 archivo = 1 corrida | Sobre el `Feature:` (`@tr-*`) | Global en el repositorio | `Rule: archivo.case.feature` + `Scenario: @tc-*` |
| **`testplan`** | 1 archivo = 1 plan | Sobre el `Feature:` (`@tp-*`) | Global en el repositorio | `Rule: archivo.run.feature` (coordinacion de runs) |
| **`bug`** | 1 archivo = N defectos | Sobre cada `Scenario:` (`@bg-*`) | Unica en el archivo | `Scenario` con `set target`, `status`, `trace`, `evidence` |

 Recursos Personalizados (*Custom Resources*)

Además de los recursos nativos (`github_testcase`, `github_testrun`, `github_testplan`), Testform permite registrar **plantillas de recursos personalizadas** para mapear escenarios Gherkin hacia cualquier API externa (Jira, Zephyr, Azure DevOps, o servicios propietarios).

### Carga Automática por Convención

Testform escanea automáticamente los archivos `.js` o `.ts` ubicados en:
- `.testform/resources/*.js` (o `./resources/*.js`).
- Módulos compartidos: `.testform/modules/**/resources/*.js`.

### Definición de un Custom Resource

```javascript
// .testform/resources/jira-testcase.js
module.exports = {
  type: 'jira_testcase',
  fields: [
    { name: 'summary', value: (scenario) => scenario.name },
    { name: 'description', value: (scenario) => scenario.description || '' },
    { name: 'priority', value: (scenario) => scenario.custom?.fields?.priority || 'Medium' }
  ],
  comments: (scenario, context) => [
    {
      identity: scenario.custom?.identity,
      status: scenario.custom?.fields?.status || 'passed',
      body: `Ejecutado automáticamente en build #${context?.buildId || 'local'}`,
      title: scenario.name
    }
  ]
};
```
