title: "Instalación y Quickstart"
---

Aprende a instalar Testform globalmente, inicializar tu espacio de trabajo y comprender el ciclo de vida del estado según el tipo de backend configurado.

## Requisitos Previos

### 1. Entorno de Ejecución Base
Antes de comenzar, asegúrate de contar con el entorno local:
- **Node.js:** versión 18.0.0 o superior instalada (`node -v`).
- **Git:** repositorio Git inicializado en tu espacio de trabajo (`git status`).
- **NPM:** gestor de paquetes para instalar el binario global de Testform (`npm -v`).

### 2. Modos de Operación y Proveedores

Testform se adapta a dos modalidades operativas según la infraestructura de tu equipo:

#### Modo Local / Offline (`provider: local`)
Si utilizas el proveedor local (`provider: local` y `backend: local`), **no requieres ninguna cuenta externa, token ni conexión a internet**. Testform opera de forma 100% autónoma y offline, guardando el ledger de pruebas en tu archivo local `testform.state` o en tu repositorio Git.

#### Modo GitHub Provider (`provider: github`)
Al conectar Testform con GitHub para sincronizar casos de prueba, ejecuciones y suites en GitHub Issues y tableros de proyectos, tu organización y repositorio deben cumplir con los siguientes requisitos:

1. **GitHub Project (Projects V2):**
   - Un proyecto de GitHub activo (a nivel de organización o usuario) vinculado al repositorio de pruebas.
   - Un campo de selección única (*Single-select field*) denominado estrictamente **`Status`**, configurado con las siguientes opciones exactas:
     - `Todo`
     - `Done`
     - `passed`
     - `failed`
     - `blocked`
     - `skipped`
     - `unexecuted`

2. **Etiquetas del Repositorio (Labels):**
   - El repositorio requiere las siguientes 5 etiquetas para clasificar automáticamente las incidencias:
     - `bug`
     - `testcase`
     - `testplan`
     - `testreport`
     - `testrun`

3. **Autenticación y Permisos del Token (PAT):**
   - Un **Personal Access Token (PAT)** con los permisos adecuados:
     - **Classic PAT:** Scopes `repo` (control total de repositorios) y `project` (lectura y escritura de proyectos).
     - **Fine-Grained PAT:** Permisos de repositorio (`Issues: Read and write`) y permisos de organización (`Projects: Read and write`).
   - El token debe exportarse en tu terminal como variable de entorno (por ejemplo, `export GITHUB_TOKEN="ghp_..."`) o configurarse mediante `testform login`.
   
   :::note
   **Nota sobre GitHub Actions:** El token por defecto `GITHUB_TOKEN` que proporciona GitHub Actions carece de permisos para manipular GitHub Projects V2 a nivel de organización. En tus pipelines de CI/CD, configura un GitHub Secret con un PAT dedicado (ej. `secrets.TESTFORM_GITHUB_TOKEN`) para permitir la sincronización automática de tableros y transiciones de estado.
   :::

4. **Configuración Automatizada con Workflow (Recomendado):**
   Para automatizar la creación de etiquetas y la vinculación del proyecto en cuestión de segundos, recomendamos utilizar el workflow oficial **Install Testform Labels and Project** (`.github/workflows/install.yml`). Este flujo automatizado:
   - Crea automáticamente las 5 etiquetas requeridas (`bug`, `testcase`, `testplan`, `testreport`, `testrun`).
   - Clona el [Proyecto Plantilla de Testform](https://github.com/users/fromeroc9/projects/4) en tu cuenta u organización y lo vincula a tu repositorio.
   - Configura el campo `Status` con todas las opciones y colores oficiales de QA.
   - Instala el workflow `close-issue.yml` para gestionar el cierre automático y transiciones de incidencias.

### 3. Drivers Opcionales para Reportes (Word y Excel)
Para preservar un binario ultra-ligero (~1 MB), los motores generadores de documentos binarios (`docx` y `exceljs`) están desacoplados como dependencias opcionales. Si vas a generar reportes en Word (`.docx`) o Excel (`.xlsx`), instálalos bajo demanda:

```bash
npm install -g docx exceljs
# O como dependencia de desarrollo en tu proyecto local:
npm install --save-dev docx exceljs
```

## Paso 1: Instalación Global

Testform es una herramienta de línea de comandos (CLI) que se instala **únicamente de forma global** en tu sistema operativo, al igual que herramientas como Terraform o Git:

```bash
npm install -g @fromeroc9/testform@beta
```

Verifica la instalacion consultando la version del binario:

```bash
testform -version
```

Salida esperada en terminal:

```text
Testform v1.1.0
on win32_x64
```

> Testform consulta automaticamente el registro de NPM para comprobar si existe una version mas reciente. Si tu CLI esta desactualizada, mostrara un aviso similar al de Terraform:
> ```text
> Your version of Testform is out of date! The latest version
> is 1.18.0. You can update by running:
>   npm install -g @fromeroc9/testform@beta
> ```

## Paso 2: Inicializar el Proyecto (testform init)

Ejecuta el comando `testform init` en la raiz de tu repositorio:

```bash
testform init
```

Salida real en consola:

```text
Initializing the backend...
Initializing Testform configuration...
- Configuration: main.yml (v1.0)
- State backend: ready

Testform has been successfully initialized!

You may now begin working with Testform. Try running "testform plan" to see
any changes that are required for your test management resources.

If you ever set or change configuration for Testform, rerun this command to
reinitialize your working directory.
```

## Paso 3: Estructura Generada y Ciclo de Vida del Estado

Al igual que en Terraform, **`testform init` genera unicamente el archivo de configuracion**. No crea archivos de estado preliminares ni carpetas ocultas.

```text
mi-proyecto/
└── main.yml            # Manifiesto principal de configuracion
```

### Ciclo de Vida en Backend Local (`backend: local`)

Cuando utilizas el backend local por defecto, los archivos de estado se crean dinamicamente segun la fase del flujo de trabajo:

1. **Tras `testform init`:**
   - Unicamente existe `main.yml`. No se crea `testform.state` ni copias de respaldo.
2. **Durante `testform plan`:**
   - Si `testform.state` aun no existe, Testform lee un estado vacio en memoria (0 recursos) y calcula las adiciones planeadas (`+ create`) en modo de solo lectura, sin escribir nada en disco.
3. **Tras el primer `testform apply`:**
   - Al aplicar los recursos con exito, se crea por primera vez `testform.state` con `serial: 1` y los metadatos de los casos conciliados. No se crea archivo `.backup` porque no habia un estado previo que respaldar.
4. **A partir del segundo `testform apply`:**
   - Antes de modificar el estado, Testform copia el estado previo a `testform.state.backup` (`serial: 1`) y escribe el nuevo estado en `testform.state` (`serial: 2`). Ambos archivos comparten exactamente el mismo formato JSON.

```text
mi-proyecto/
├── main.yml            # Manifiesto principal de configuracion
├── testform.state          # Estado activo (creado tras el primer apply)
└── testform.state.backup   # Respaldo automatico (creado a partir del segundo apply)
```

### Ciclo de Vida en Backends Remotos (`s3`, `oci`, `azurerm`, `gcs`)

Cuando configuras un backend en la nube en tu `main.yml`:

```text
mi-proyecto/
└── main.yml            # Manifiesto principal de configuracion
```

- **Sin archivos de estado locales:** En ningun momento se generan archivos `testform.state` ni `testform.state.backup` en tu disco local.
- **Persistencia en la Nube:** Las operaciones de lectura y escritura (`s3.putObject`, `UploadBlob`, etc.) se comunican de forma directa y atomica con el bucket remoto.
- **Repositorio Git Limpio:** Tu espacio de trabajo queda 100% libre de archivos de estado locales, previniendo conflictos en Pull Requests y filtraciones de credenciales.
- **Respaldos Nativos:** La recuperacion ante desastres y el historial de cambios se gestionan con el Versionado de Objetos nativo (*Bucket Versioning*) del proveedor cloud.
