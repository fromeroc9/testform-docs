Automatiza la validación y conciliación de casos de prueba en cada Pull Request y despliegue a la rama principal.

## Flujo de Trabajo Recomendado

1. **En Pull Requests:** Ejecuta `testform init -lock=false`, `testform validate` y `testform plan -lock=false`. El resultado del plan se publica automáticamente como comentario en el PR para revisión por pares sin escribir locks ni mutar el estado remoto.
2. **Al Fusionar en Main:** Ejecuta `testform init` y `testform apply -auto-approve` (o el plan guardado) para sincronizar de forma atómica los cambios aprobados con los proveedores y actualizar el backend de estado.

## Archivo de Workflow Estándar (.github/workflows/testform.yml)

```yaml
name: Testform CI/CD

on:
  pull_request:
    paths:
      - 'tests/**'
      - 'testcase/**'
      - 'main.yml'
  push:
    branches:
      - main
    paths:
      - 'tests/**'
      - 'testcase/**'
      - 'main.yml'

jobs:
  testform:
    name: Testform Plan & Apply
    runs-on: ubuntu-latest

    permissions:
      contents: read
      pull-requests: write

    steps:
      - name: Checkout del Repositorio
        uses: actions/checkout@v4

      - name: Configurar Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20

      - name: Instalar Dependencias
        run: npm ci

      - name: Inicializar Testform (Solo Lectura en PR)
        if: github.event_name == 'pull_request'
        env:
          GITHUB_TOKEN: ${{ secrets.TESTFORM_STATE_TOKEN || secrets.GITHUB_TOKEN }}
        run: npx testform init -lock=false

      - name: Inicializar Testform (Push a Main)
        if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        env:
          GITHUB_TOKEN: ${{ secrets.TESTFORM_STATE_TOKEN || secrets.GITHUB_TOKEN }}
        run: npx testform init

      - name: Validar Sintaxis y Politicas
        run: npx testform validate

      - name: Generar Plan de Ejecucion (Pull Request)
        if: github.event_name == 'pull_request'
        id: plan
        env:
          GITHUB_TOKEN: ${{ secrets.TESTFORM_STATE_TOKEN || secrets.GITHUB_TOKEN }}
        run: |
          npx testform plan -lock=false -no-color > plan.txt
          echo "PLAN<<EOF" >> $GITHUB_ENV
          cat plan.txt >> $GITHUB_ENV
          echo "EOF" >> $GITHUB_ENV

      - name: Comentar Plan en Pull Request
        if: github.event_name == 'pull_request'
        uses: actions/github-script@v7
        with:
          github-token: ${{ secrets.GITHUB_TOKEN }}
          script: |
            const planOutput = process.env.PLAN;
            const body = `#### Resultado de Testform Plan \n\`\`\`text\n${planOutput}\n\`\`\``;
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: body
            });

      - name: Aplicar Cambios Aprobados (Push a Main)
        if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        env:
          GITHUB_TOKEN: ${{ secrets.TESTFORM_STATE_TOKEN || secrets.GITHUB_TOKEN }}
        run: npx testform apply -auto-approve
```

## Workflow Avanzado con Binario de Plan (.github/workflows/testform-plan.yml)

Para pipelines empresariales donde se prohíben discrepancias entre lo revisado en el Pull Request y lo aplicado en producción:

```yaml
name: Testform Speculative Plan & Apply

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  plan:
    name: Plan Speculative Diff
    runs-on: ubuntu-latest
    if: github.event_name == 'pull_request'
    permissions:
      contents: read
      pull-requests: write
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - name: Initialize & Run Testform Plan with Binary Output
        env:
          TESTFORM_GITHUB_TOKEN: ${{ secrets.TESTFORM_GITHUB_TOKEN }}
        run: |
          npx testform init -lock=false
          npx testform plan -lock=false -out=tfplan.bin -detailed-exitcode || exit_code=$?
      - name: Upload Execution Plan
        uses: actions/upload-artifact@v4
        with:
          name: tfplan
          path: tfplan.bin
          retention-days: 7

  apply:
    name: Apply Approved Plan
    runs-on: ubuntu-latest
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - name: Initialize & Apply Direct
        env:
          TESTFORM_GITHUB_TOKEN: ${{ secrets.TESTFORM_GITHUB_TOKEN }}
        run: |
          npx testform init
          npx testform apply -auto-approve
```

## Arquitectura CI/CD con Ramas Protegidas y Backend `github`

En equipos donde los ingenieros QA **únicamente suben cambios en archivos `.feature`** mediante Pull Requests sobre una rama `main` protegida (*Branch Protection Rules*), nunca es necesario que los QA tengan acceso de push directo a `main` ni permisos de escritura sobre el estado:

1. **Los QA trabajan solo en `.feature`:** Crean su rama, editan escenarios Gherkin y abren un Pull Request hacia `main`.
2. **En el Pull Request (solo lectura):** El workflow ejecuta `testform init -lock=false` y `testform plan -lock=false` para comentar el impacto del cambio en el PR **sin crear archivos `.lock` ni escribir commits en el backend**.
3. **Al aprobar y hacer merge a `main`:** El pipeline ejecuta `testform init` y `testform apply -auto-approve` con un secreto de repositorio (por ejemplo `secrets.TESTFORM_STATE_TOKEN`) que tiene permisos sobre el backend de estado.

### ¿Cómo evitar bloqueos de Branch Protection al usar `backend.github`?

Como `backend.github` guarda `testform.state` y `<path>.lock` mediante commits en la rama configurada:

- **Opción A — Repositorio dedicado para el estado (Recomendado):** Apunta `backend.github.repository` a un repositorio separado exclusivo para el estado (por ejemplo `"mi-org/testform-state"`). Así `main` del proyecto QA conserva todas sus reglas de protección intactas, mientras que el secreto de CI escribe únicamente en el repositorio de estados.
- **Opción B — Rama huérfana no protegida en el mismo repo:** Usa `branch: "testform-state"` (el valor por defecto) en lugar de `main`, manteniendo `main` protegida para el código y dejando `testform-state` restringida solo al token del pipeline.
- **Opción C — Lista de Bypass:** Si la rama de estado debe estar protegida, agrega la GitHub App o usuario bot del token de CI en *Allow specified actors to bypass required pull requests* dentro de la configuración de Branch Protection.

:::caution[Importante: Token de GitHub Actions y GitHub Projects V2]
El token generado automáticamente por GitHub Actions (`secrets.GITHUB_TOKEN`) tiene permisos restringidos al repositorio actual y **no puede mutar tableros de GitHub Projects (Projects V2)** a nivel de organización o usuario.

Si tu configuración utiliza `provider: github` sincronizado con tableros de GitHub Projects:
1. Crea un **Personal Access Token (PAT)** con permisos de `repo` y `project`.
2. Guárdalo como un GitHub Secret en tu repositorio (por ejemplo, `TESTFORM_GITHUB_TOKEN`).
3. Sustituye `${{ secrets.GITHUB_TOKEN }}` por `${{ secrets.TESTFORM_GITHUB_TOKEN }}` en las etapas de `plan` y `apply`.
:::

## Flujo por Pull Requests con `provider: local`

Cuando el proyecto utiliza `provider: local`, todas las incidencias simuladas se guardan secuencialmente (`local:1`, `local:2`, ...) en `.testform/data.json` y el estado reconciliado se guarda en `testform.state`.

Si dos desarrolladores ejecutan `testform apply` en ramas distintas antes del PR y suben esos archivos JSON, ambos asignarán los mismos IDs incrementales y producirán **conflictos de merge en `testform.state` y `.testform/data.json`**.

Para manejar Pull Requests limpiamente con `provider: local`:

1. **En las ramas de PR (antes del merge):**
   - Modifica únicamente los archivos `.feature`, `main.yml` o `*.vars.yml`.
   - Ejecuta solamente `testform validate` y `testform plan` (comandos de solo lectura que no modifican `testform.state` ni `data.json`).
   - En el pipeline del PR, el paso de `plan` publica el diff para revisión por pares sin mutar ningún archivo JSON.
2. **Al hacer merge a `main`:**
   - **Si versionas estado en Git (`backend: local`):** ejecuta `testform apply -auto-approve` únicamente sobre `main` (manualmente o en el job `push` a `main` haciendo commit de `testform.state` y `.testform/data.json`, asegurándote de no ignorar `data.json` en `.gitignore`).
   - **Si trabajas en modo efímero:** agrega `testform.state`, `.testform/data.json` y `.testform/cache/` a `.gitignore`; cada PR viaja solo con `.feature` + `main.yml` y CI o cada entorno reconstruye el estado cuando lo necesite con `testform apply -auto-approve`.
3. **Para equipos con múltiples PRs simultáneos:** considera migrar a `provider: github` (o `gitlab`) junto a un [backend remoto](../language/backends) con bloqueo de estado distribuido (S3, GCS, Azure Blob).
