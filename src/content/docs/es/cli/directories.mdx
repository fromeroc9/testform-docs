---
title: "El Directorio .testform y ~/.testform.d"
description: "Estructura, propósito y ciclo de vida del directorio de trabajo local .testform y la configuración global ~/.testform.d."
---

Al igual que HashiCorp Terraform utiliza `.terraform` y `~/.terraform.d`, **Testform** utiliza dos directorios de soporte para gestionar su estado operativo, cachés locales, extensiones y credenciales de usuario:

1. **`.testform/` (Directorio de Proyecto):** Creado en la raíz del espacio de trabajo donde reside `main.yml`. Es el área de trabajo local donde Testform almacena metadatos del backend, módulos descargados, sandboxes efímeros y extensiones descubiertas.
2. **`~/.testform.d/` (Directorio Global de Usuario):** Ubicado en el directorio personal (*home*) del usuario del sistema operativo. Almacena credenciales de autenticación y configuraciones de sesión persistentes.

---

## Estructura del Directorio de Proyecto (`.testform/`)

```text
mi-proyecto/
├── main.yml
├── testform.state
├── .testform.lock.hcl         # Lockfile criptográfico de proveedores (hashes h1: y versiones fijadas)
└── .testform/
    ├── data.json              # Base de datos simulada del proveedor local (provider: local)
    ├── environment            # Nombre del workspace actualmente seleccionado
    ├── cache/                 # Archivos temporales y de caché descartable del motor
    │   ├── backend.json       # Configuración del backend activo inicializado (testform init)
    │   ├── lock.json          # Lock file de dependencias y checksums de providers
    │   └── parser-ast.json    # Caché incremental de AST para parseo rápido (.feature)
    ├── providers/             # Plugins de proveedores descargados e instalados (testform init)
    │   └── <nombre_proveedor>/
    │       ├── index.js / provider.ts
    │       └── package.json
    ├── modules/               # Módulos remotos descargados desde repositorios Git
    │   └── <nombre_modulo>/
    │       ├── main.yml
    │       ├── policies/      # Políticas heredadas del módulo compartido
    │       └── resources/     # Plantillas de recursos del módulo compartido
    ├── policies/              # Políticas de validación personalizadas locales (.ts, .js)
    ├── resources/             # Plantillas de recursos personalizadas locales (.ts, .js)
    ├── reports/               # Extensiones de reportes (.ts), formatos (.format.ts) y plantillas (.docx, .xlsx)
    ├── backends/              # Drivers de backends personalizados locales
    └── ephemeral/             # Metadatos de sandboxes efímeros activos (testform ephemeral)
```

## Componentes y Archivos en la Raíz del Proyecto

### `.testform.lock.hcl`
- **Cuándo se genera:** Durante `testform init` al resolver `testform.required_providers`.
- **Propósito:** Registra las versiones exactas y los hashes criptográficos SHA-256 (`h1:<base64>`) de cada proveedor descargado. Garantiza compilaciones deterministas e idénticas en todas las máquinas del equipo y en pipelines de CI/CD.

## Componentes y Archivos en `.testform/`

### 1. `cache/backend.json`
- **Cuándo se genera:** Durante la ejecución de `testform init`.
- **Propósito:** Almacena la configuración activa y el hash del backend configurado (tipo de almacenamiento, bucket, región o parámetros de conexión) dentro del directorio de caché.
- **Mecanismo de seguridad:** Si modificas el bloque `backend` en `main.yml` o pasas banderas `-backend-config` divergentes, Testform compara los valores contra `.testform/cache/backend.json` y detiene la ejecución para evitar corrupción de estado, solicitando ejecutar `testform init -reconfigure` o `testform init -migrate-state`.

### 2. `environment`
- **Cuándo se genera:** Al gestionar espacios de trabajo mediante `testform workspace new <nombre>` o `testform workspace select <nombre>`.
- **Propósito:** Archivo de texto plano de una sola línea que indica cuál es el workspace activo del directorio actual (por ejemplo: `staging` o `production`). Si no existe, Testform opera en el workspace por defecto (`default`).

### 3. `providers/`
- **Cuándo se genera:** Durante `testform init` cuando `main.yml` declara fuentes en `testform.required_providers`.
- **Propósito:** Directorio exclusivo donde Testform descarga y aloja los plugins ejecutables de cada proveedor (desde Git subpaths, repositorios completos o paquetes npm). El cargador dinámico de Testform (`src/providers/loader.ts`) ejecuta el código desde aquí.

### 4. `modules/`
- **Cuándo se genera:** Durante `testform init`, cuando `main.yml` declara módulos con fuentes remotas (`git::https://...`).
- **Propósito:** Almacena copias locales congeladas de los módulos de prueba. Permite que las ejecuciones posteriores de `testform plan` y `testform apply` funcionen de forma determinista y sin depender de conexión constante a la red o a servidores de control de versiones.

> [!NOTE]
> Testform también inspecciona automáticamente las carpetas `policies/` y `resources/` dentro de cada módulo descargado en `.testform/modules/<nombre>/`, heredando reglas corporativas de calidad sin configuración adicional.

### 4. `policies/`
- **Cuándo se utiliza:** Creado manualmente por ingenieros de QA o equipos de gobernanza.
- **Propósito:** Contiene reglas de validación en TypeScript o JavaScript (`.ts`, `.js`, `.mjs`, `.cjs`) registradas mediante la API `registerPolicy()`. Testform auto-descubre y evalúa estas políticas durante `testform validate` y `testform apply`.

### 5. `resources/`
- **Cuándo se utiliza:** Creado para extender conectores o mapeos de recursos hacia sistemas externos (Jira, Azure DevOps, TestRail, APIs internas).
- **Propósito:** Contiene definiciones de recursos (`registerResource()`) que Testform compila y carga dinámicamente en tiempo de ejecución.

### 6. `cache/`
- **Cuándo se genera:** De manera automática en tiempo de inicialización (`testform init`) o parseo incremental.
- **Propósito:** Almacena artefactos autogenerados y temporales del motor de Testform estrictamente descartables:
  - `backend.json`: Configuración activa y hash del backend inicializado.
  - `lock.json`: Archivo de bloqueo de dependencias de proveedores con sus checksums criptográficos calculados.
  - `parser-ast.json`: Caché incremental del parser Gherkin (`AstCache`); es 100% descartable y se regenera automáticamente.
- **Aislamiento de seguridad:** Al concentrar los archivos temporales dentro de `cache/`, se evita cualquier riesgo de sobreescribir o borrar accidentalmente código de usuario en `.testform/policies/`, `.testform/resources/` o `.testform/reports/`. Además, permite agregar `.testform/cache/` a `.gitignore` de forma directa y limpia sin excepciones complejas.

### 7. `data.json`
- **Cuándo se genera:** Durante `testform apply` cuando el proyecto utiliza `provider: local`.
- **Propósito:** Almacena la base de datos simulada del proveedor local (incidencias creadas, ejecuciones, comentarios, enlaces y campos personalizados).
- **Persistencia en Git:** A diferencia del contenido de `cache/`, `data.json` reside directamente en `.testform/data.json` para que pueda versionarse en Git cuando se desea conservar el historial del proveedor local entre colaboradores o en CI/CD, sin colisionar con las cachés descartables.
- **Migración automática:** Si un proyecto existente contiene la ruta anterior `.testform/cache/data.json`, Testform lo detecta automáticamente, lo migra a `.testform/data.json` y continúa funcionando de forma transparente.

### 8. `reports/`
- **Cuándo se utiliza:** Creado para extender el motor analítico de `testform report`.
- **Propósito:**
  - **Reportes personalizados:** Archivos `<nombre>.ts` que implementan `IReport`.
  - **Formatos personalizados:** Archivos `<formato>.format.ts` que implementan `IReportFormat` (por ejemplo, exportadores a Slack, PDF o XML).
  - **Plantillas canónicas:** Archivos `report.docx` o `report.xlsx` ubicados en esta carpeta se cargan automáticamente como plantilla predeterminada sin necesidad de pasar el argumento `-template`.

### 9. `ephemeral/`
- **Cuándo se genera:** Al invocar `testform ephemeral up`.
- **Propósito:** Almacena los identificadores de sesión, puertos y metadatos de los sandboxes temporales de prueba desplegados en ramas de CI/CD, permitiendo su inspección con `testform ephemeral list` y su posterior limpieza con `testform ephemeral down`.

### 10. `backends/`
- **Cuándo se utiliza:** Para almacenar drivers de backend personalizados locales (`.ts` / `.js`) que implementan la interfaz `IBackend`.

## El Directorio Global de Usuario (`~/.testform.d/`)

A nivel de máquina de desarrollo o agente de ejecución de CI/CD, Testform mantiene una configuración global independiente de los repositorios:

- **Linux / macOS:** `~/.testform.d/`
- **Windows:** `C:\Users\<usuario>\.testform.d\`

### Archivo `credentials.json`
- **Cuándo se genera:** Al ejecutar `testform login <hostname>` (por ejemplo: `testform login github.com`).
- **Cuándo se modifica:** Al ejecutar `testform logout <hostname>`.
- **Propósito:** Almacena de forma segura los tokens de autenticación de proveedores (ej. Personal Access Tokens de GitHub o GitLab) para que el CLI pueda interactuar con las APIs remotas sin requerir exportar variables de entorno en cada terminal:

```json
{
  "hosts": {
    "github.com": {
      "token": "ghp_xxxxxxxxxxxxxxxxxxxx"
    }
  }
}
```

## Configuración en `.gitignore`

Lo que debes ignorar en Git depende de si utilizas un proveedor remoto (`github` / `gitlab`) o `provider: local`, y de si compartes extensiones locales dentro de `.testform/`:

### Escenario A: Proveedor remoto (`github`, `gitlab`) o uso efímero de `provider: local`

Los artefactos generados por `testform init` y las cachés temporales no deben subirse al repositorio:

```text
# Directorios generados y cachés de Testform
.testform/cache/
.testform/providers/
.testform/modules/
.testform/ephemeral/
.testform/environment

# Archivos de plan binarios, locks y backups de estado
*.tfplan
*.backup
testform.state.lock

# Si trabajas con provider: local en modo efímero (sin versionar estado ni base de datos local),
# descomenta también:
# testform.state
# .testform/data.json
```

> [!NOTE]
> Las carpetas `.testform/policies/`, `.testform/resources/`, `.testform/reports/` y `.testform/backends/` contienen código y plantillas creadas por tu equipo, por lo que **sí deben versionarse en Git** cuando existan.

### Escenario B: `provider: local` con persistencia de estado en Git (`backend: local`)

Si decides versionar `testform.state` en Git usando `provider: local`, **debes versionar también `.testform/data.json`**:

```text
# Cachés temporales del motor
.testform/cache/
.testform/providers/
.testform/modules/
.testform/ephemeral/
.testform/environment
testform.state.lock

# Archivos a versionar en Git para preservar la base de datos y ledger del proveedor local:
# - testform.state
# - .testform/data.json
```

> [!CAUTION]
> Si subes `testform.state` al repositorio pero ignoras `.testform/data.json`, al clonar el proyecto y ejecutar `testform plan`, `testform apply` o `testform refresh` (que ejecutan `refresh` por defecto), Testform no encontrará los issues en `data.json`, **eliminará esos recursos de `testform.state`** y volverá a crearlos desde `#1` en la nueva máquina (con nuevas fechas y sin comentarios previos). Tus archivos `.feature` y `main.yml` no se pierden, pero la continuidad de `data.json` y del ledger sí se reinicia.

> [!WARNING]
> Nunca agregues ni confirmes el archivo `~/.testform.d/credentials.json` a un repositorio público o compartido, ya que contiene credenciales de acceso sensibles.

## Regeneración y Recuperación

Si el directorio `.testform/` se elimina accidentalmente o se clona el proyecto en una nueva máquina:

1. Ejecuta `testform init`.
2. Testform reconstruirá automáticamente la estructura base, recreará `.testform/cache/backend.json` y descargará nuevamente los módulos declarados en `.testform/modules/`.
3. Si el proyecto utilizaba un workspace diferente a `default`, selecciónalo con `testform workspace select <nombre>`.
4. Si usas `provider: local` sin haber versionado `.testform/data.json`, ejecuta `testform apply` para regenerar la base de datos local y `testform.state` a partir de tus archivos `.feature`.
